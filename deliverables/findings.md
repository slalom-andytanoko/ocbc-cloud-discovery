| 7 | Medium | **Scope reduction, not a documentation gap.** v1.2/CS-053 specified a validation chain that included schema-drift detection and a data-owner (ownership) verification check. v1.3 (31 Jul 2026) formally defers both to the backlog: schema change detection (BL-005, CS-013) and data owner verification (BL-006, CS-057) are not built in the current release. | 8 | Medium | **Physical microservice decomposition changed after (potentially) implementation had already started.** [[reference/data-acquisition-cloud-sync-detailed-design]] (DRAFT v0.1, 2026-08-03) formally closes decision D03 with a **five-component** decomposition — Orchestrator, Worker, Sync Push Service, Operations Service, Scheduler Job Adapter — built on a database-as-task-queue model with no persistent lease. This **replaces** the four-service split (Integration/Control/Security/Orchestration Service) this wiki had documented as the working model since v1.1 (24 Jul 2026), including a persistent-lease-with-TTL design in v1.3 §9.7.2 that DD-06 explicitly supersedes. If any implementation team has already built services against the older four-service/lease model, reconciling to the new decomposition (service boundaries, database schema/table-ownership, and the lease-vs-DB-task-queue concurrency mechanism) is a non-trivial rework, not a rename. Recommend confirming with the delivery team whether any code has been built against the superseded model before treating D03 as fully closed for delivery purposes. **Update 2026-08-03: this rework has now been carried out** — `integration-service`'s `FileDropWatcher` was redirected to call orchestration-service's real `/orchestration/runs/initiate` endpoint, the now-orphaned `control-service` MVP stub was deleted entirely (module, docker-compose, gateway routes, Terraform, scripts, docs), and all remaining services were consolidated onto one shared `dataacq` database. Verified via a clean full reactor build and a live smoke test (file-drop → real run → `COMPLETED` status). | External: Re__IaC_Deployment_Process/OCBC Data Acquisition - Cloud Sync Detailed Design.md ([[reference/data-acquisition-cloud-sync-detailed-design]]) | Architecture / Delivery Risk | Resolved (code) | — |
| 9 | High | **Hardcoded plaintext database credential committed in source.** `ocbc-data-acquisition-service/terraform/variables.tf` declares `variable "db_password"` with a plaintext default value (`sensitive = false`) checked into the repository, rather than sourcing the credential from a secrets manager, environment variable, or a `sensitive = true` variable with no default. This is a real, unresolved OWASP-relevant hardcoded-credential exposure against the live RDS instance referenced by `var.db_host` (`ocbc-db.craoma6wm41r.ap-northeast-1.rds.amazonaws.com`) and should be remediated before this repo/state is considered production-ready — ideally by rotating the real RDS password and switching Terraform to pull it from AWS Secrets Manager / SSM Parameter Store. | Code: ocbc-data-acquisition-service/terraform/variables.tf | Security / Secrets Management | Open | — |
| 10 | Medium | **Manual database consolidation required against the real, already-deployed RDS instance.** The Terraform in `ocbc-data-acquisition-service` does not provision the RDS instance itself (no `aws_db_instance` resource) — it only references an existing instance via `var.db_host`.
